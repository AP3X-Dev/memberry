Hardened readJsonBody in packages/mcp/src/server.ts (edit clone amp-opt, branch opt/memberry-hardening) against memory-exhaustion DoS. Before: readJsonBody buffered the entire POST body via `for await (const chunk of req)` with no byte cap, then Buffer.concat + JSON.parse (server.ts:399-408 original). Fix: added DEFAULT_MAX_REQUEST_BODY_BYTES=1_000_000 (1 MB) constant and a `RequestBodyTooLargeError extends Error` typed error (module level, exported). In startSSE, resolve maxBodyBytes via readEnv('MEMBERRY_MAX_BODY_BYTES') (legacy fallback AMP_MAX_BODY_BYTES; invalid/non-positive falls back to default). readJsonBody now: (1) early-rejects if Content-Length header > cap (throws before reading body); (2) streaming backstop tracks accumulated bytes in the for-await loop and throws BEFORE buffering the over-cap chunk. The /mcp POST catch block distinguishes RequestBodyTooLargeError → sendMcpJsonError(res, 413, 'Payload too large', -32600), then req.destroy() AFTER writing the response (order matters: destroying first would race the 413 off the wire); otherwise → 400 Parse error -32700 (unchanged). Key gotcha discovered: a lying-smaller-Content-Length cannot be tested via the size check because Node's HTTP parser only delivers Content-Length bytes to the request stream (rest stays in socket buffer → JSON.parse fails → 400, not 413). The real streaming-backstop DoS vector is Transfer-Encoding: chunked with no Content-Length; the test uses node:http with no content-length so Node sends chunked. Added 3 vitest tests in server.test.ts: Content-Length early-reject 413, chunked-no-CL streaming-backstop 413, small-body happy-path 200. Tests use AMP_MAX_BODY_BYTES=1024 env to lower the cap deterministically (no gigabyte allocation). Cap only applies to POST body reading — no regression to /mcp, /messages, auth/CORS/healthz, or OPT-02 session-binding tests.
